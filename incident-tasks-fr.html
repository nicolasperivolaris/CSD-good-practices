Guide · Incident Tasks

Une Task, une action, un service.

Une Incident Task demande à un autre service une action précise pour résoudre un incident. L'incident, lui, reste à vous.

Task ou autre chose ? avant de créer

Situation
Un autre service doit faire une action précise, sans approbation, et l'incident reste chez moiex. vérifier les logs d'un switch, intervenir sur siteIncident Task
Tout l'incident relève d'un autre serviceex. l'application est gérée par une autre équipeRéassigner
L'action modifie la production ou demande une approbationex. ouvrir un flux firewall, changer une configuration serveurChange
L'utilisateur demande quelque chose de nouveauex. accès à un dossier, nouveau matérielRITM
J'ai juste une question ou une info à demander@ Work notes

Une bonne Task à la création

  1. Une action, un serviceUne Task = une action pour un seul groupe. Deux actions ou deux groupes : deux Tasks.
  2. Le bon groupeVérifier le groupe d'assignation avant d'envoyer : une Task mal routée part en ping-pong.
  3. La Short description décrit l'action« Vérifier les logs du switch SW-03 », pas « Problème réseau ».
  4. Une description complèteCe qu'on attend, et le contexte : symptôme, ce qui a déjà été fait. Pas besoin de relire tout l'incident.
  5. Prévenir quand c'est finiCelui qui traite la Task la ferme avec le résultat dans les Work notes : le propriétaire de l'incident peut avancer.
  6. La bonne prioritéCelle de l'impact de l'incident, pas plus haute pour passer devant.
